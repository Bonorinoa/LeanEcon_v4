# B2 bounded-search spike (2026-08-08) — is naive tactic search trustworthy?

Question: does a generic bounded tactic chain (`first | trivial |
simp [defs] | exact? | apply? | aesop`) make real progress on
reviewer-authored statements against the pinned kernel — or does it
degenerate into patches/vacuity? This spike was run BEFORE any B2 design
gate (CTO sandbox-toy-first preference), to decide whether wiring
`Capability.PROVE_OR_REPAIR` is worth it.

## Method (two signals per target — the key design decision)

Targets: 8 reviewer-authored statements with proofs stripped (c1, c2, c3,
c4, oos1a, oos1b, oos2, fwt1), each compiled as
`theorem ... := by first | trivial | simp [defs] | exact? | apply? | aesop`
(+ `linarith` on arithmetic targets) in `lean_workspace/.a3-candidates/b2-spike/`.

1. **Bare signal:** `lake env lean <file>` exit code (walkthrough-era
   "compiles" check).
2. **Authoritative signal:** append `#print axioms B2Spike.<name>` and scan
   for `sorryAx` — mirrors `verifier.py`'s kernel audit.

Predictions recorded first (`artifacts/local/b2-spike-2026-08-08-expectations.md`):
4–5/8 passes expected on the trivial class; fwt1/oos1b expected FAIL.

## Results (authoritative)

| Target | Bare compile | Axiom audit | Verdict |
|---|---|---|---|
| c1 | PASS 8.9s | clean | GENUINE PASS (`exact?` → `exact h`) |
| c2 | PASS 21.1s | clean | GENUINE PASS |
| c3 | PASS 15.6s | clean | GENUINE PASS |
| c4 | PASS 16.3s | clean | GENUINE PASS |
| oos1a | PASS 8.7s | clean | GENUINE PASS (`simp` → `of_eq_true …`) |
| oos1b | PASS 32.4s | **sorryAx** | **SORRY_CONTAMINATED — false pass** |
| oos2 | FAIL 8.9s | sorry body (failed decl) | HONEST FAIL — strict-superset witness needs `ssubset_iff_subset_not_subset` + witness construction, not searchable bare |
| fwt1 | PASS 39.6s | **sorryAx** | **SORRY_CONTAMINATED — false pass** |

Predictions vs actuals: 5 ✅ / 3 informative ⚠️ (both "worse-than-expected"
cases were the contaminated passes).

## The critical finding

**Bare `lake env lean` exit code is NOT a trustworthy pass signal.**

- `apply?` "closed" fwt1 and oos1b with proof terms literally containing
  `sorry` (`fun … h => sorry`) — exit code **0**.
- `simp [attainableSet]` on c1 in isolation also produced a `sorry` body
  after failing to close (the chain's `exact?` rescued c1 legitimately).
- `exact?` on fwt1/oos1b failed honestly, but its suggestions referenced
  the theorem being defined (`exact fresh_fwt1 h`) — circular-proof hazard
  if suggestions were auto-applied.
- Only the `#print axioms` / `sorryAx` audit separates genuine from
  contaminated. This is exactly why `verifier.py` runs the kernel audit and
  why `VERIFIED` is bundle-gated, not compile-gated.

## Consequences for a future B2 / proof-assist build

1. **Never gate B2 success on "compiles".** The kernel axiom audit
   (`#print axioms` → `sorryAx` check) MUST be the success gate, identical
   to the v1 verifier path. Candidates failing the audit are FAILED
   regardless of exit code.
2. Naive search's honest ceiling: first-draft assistant for the **trivial /
   one-liner class** (5/8 here) + kernel-diagnostics feedback for the
   structured class. NOT a prover.
3. Budget the loop; surface `sorryAx`/kernel errors verbatim; reviewer owns
   the final proof (v1 constitution unchanged).

## Ops notes from running the spike

- `library_search` does not exist in Mathlib v4.32.2 — it was replaced by
  the `exact?`/`apply?` family. Use `apply?` in chains.
- Theorems declared inside `namespace B2Spike` need qualified names in
  `#print axioms` (`#print axioms B2Spike.fwt1`).
- A FAILED declaration still gets a `sorry` body in the environment, so a
  failed target's axiom audit may show `sorryAx` too — check rc first,
  then audit (verdict: rc≠0 → FAIL regardless of audit text).
- Tactic chains with `first |` can hide which primitive closed the goal;
  bisect by rewriting the file with a single primitive per compile.
